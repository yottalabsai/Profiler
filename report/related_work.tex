\section{Related Work}
\label{sec:related}

\paragraph{GPU profiling infrastructure.}
\texttt{torch.profiler} and its Kineto backend \cite{kineto2021} record operator-level wall-clock
durations and Chrome traces, but expose no hardware performance counters---leaving practitioners
unable to distinguish memory-bound from compute-bound operators programmatically. NVIDIA Nsight
Systems~\cite{nsightsystems} captures the kernel timeline with NVTX annotations, but produces
no operator-level view: every kernel appears by its internal CUDA name (\eg
\texttt{cutlass\_80\_simt\_sgemm\_128x32\_tn}), with no indication of which PyTorch operator
launched it. NVIDIA Nsight Compute~\cite{nsightcompute} collects per-kernel hardware counters
at full precision, but its output is keyed on kernel names and invocation indices in the
replay timeline---again, no awareness of the operator graph. These three tools each solve
a distinct subproblem; \sys's contribution is the bridge that combines all three into a
unified per-operator hardware profile. NVIDIA DCGM and Dynolog~\cite{dynolog2023} target
cluster-level monitoring rather than per-operator attribution. \sys is the first
\emph{published} system to automatically attribute \ncu hardware counters to
\texttt{aten::} operators via NVTX enclosure and invocation-order matching; NVIDIA internal
tools may provide related capabilities, but no public system with comparable scope has been
described in the literature.

\paragraph{Deep learning compilers.}
TorchDynamo and TorchInductor~\cite{pytorch2024} compile PyTorch programs to Triton kernels using
heuristic fusion rules (pointwise chaining, matmul epilogue fusion), but do not incorporate
hardware counter feedback in pass selection.  \sys wraps Inductor as a downstream delegate and
inserts hardware-evidence-motivated FX passes \emph{before} Inductor's lowering step, creating a
feedback loop that Inductor alone lacks.  TVM~\cite{tvm2018} and Halide~\cite{halide2013} optimize
tensor programs via measurement-based auto-tuning and schedule/algorithm separation respectively;
neither uses per-kernel hardware counters to decide which optimization class to apply.
ONNX Runtime and TensorRT perform layer fusion and quantization but present black-box interfaces
that cannot be extended for custom architectures or augmented with profiling evidence.

\paragraph{Attention and fused kernel libraries.}
FlashAttention~\cite{flashattention2022} and FlashAttention-2~\cite{flashattention2023} tile
attention computation to keep the $[B, H, S, S]$ attention matrix in on-chip SRAM, eliminating
DRAM round-trips and register-spill pressure.  \sys implements a FlashAttention substitution pass
triggered by \texttt{local\_memory\_spills $> 0$} and \texttt{l2\_hit\_rate $< 20\%$}; this pass
was not triggered in the evaluated workloads because the Blackwell SDPA bottleneck is Tensor Core
idle (FP32 $\to$ BF16 promotion), not register spills.  xFormers~\cite{xformers2022} provides a
static library of fused attention variants; \sys is complementary: it determines \emph{which}
variant is warranted for a specific operator's hardware counter profile. Triton~\cite{triton2019} provides the JIT compilation
framework underlying Inductor kernels; \sys additionally \emph{parses} Triton kernel names to
recover fused operator identity when NVTX annotation is unavailable.

\paragraph{Profile-guided optimization.}
Classic PGO in C/C++ compilers (GCC, LLVM) collects branch frequency profiles to guide inlining
and layout decisions \cite{autofdo2016}.  \sys applies the same principle at the operator level:
hardware counter profiles select FX graph transformations.  The optimization layer is a downstream
application of the attribution pipeline described in \secref{sec:pgo}.

\paragraph{Inference optimization frameworks.}
vLLM~\cite{vllm2023} and SGLang~\cite{sglang2024} achieve high LLM serving throughput via
PagedAttention, continuous batching, and memory pooling.  These frameworks operate at the
scheduling level; their hand-coded kernels (BF16 GEMMs, FlashAttention-2) represent the
operator-level optimizations that the \sys attribution pipeline \emph{surfaces and motivates
automatically} from hardware counter evidence for arbitrary model architectures.  The two
systems are complementary: \sys can profile a workload running inside vLLM to provide
operator-attributed hardware counter data for identifying residual kernel-level inefficiencies
not covered by serving-layer scheduling.
